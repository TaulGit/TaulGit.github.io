01

从什么问题出发

The question

生成一份行程之后，
规划才真正开始。

旅行需求经常不完整，工具也会返回空结果。用户可能临时改预算，或关掉页面后再回来。系统需要知道目前掌握了什么、哪些约束尚未满足，以及接下来该由谁决定。

推荐，有没有依据？

让地点来自检索证据，禁止模型用没有检索到的 POI 补齐行程。

条件，能不能满足？

把地点、时长和估算费用交给代码校验，让失败产生可执行的修复反馈。

中断，能不能继续？

把需求澄清与人工审核变成真正的持久暂停，而不是一个等待状态标签。

02

让自主性有边界

The approach

模型负责选择，
工作流负责把事情接住。

外层状态图确定阶段和终态；研究 Agent 在各自上下文里根据工具结果决定检索词、是否重试和何时停止。两者配合，让系统既能决策，也能被检查。

05

用户审核

确认、修改或结束
Command resume

独立研究，有界工具决策

主管把需求拆为最多 3 个任务，通过 Send 动态分发。每个研究 Agent 最多 3 次模型尝试和 3 次工具尝试，允许在空结果或异常后改词检索，结果按来源归并。

结构正确，再检查事实

结构化输出只约束数据形状。校验器继续检查 POI 引用、重复地点、连续路段、时长与估算预算；不满足时反馈具体问题，达到修复上限则如实结束。

把暂停保存下来

SQLite Checkpointer 留存图状态，interrupt / Command 连接补充需求与审核。页面刷新读取服务端快照；进程重启从检查点继续。对外部只读请求，承认故障后可能重放。
